# Нереализованное и известные ограничения

Найденное тестами и ревью, что сознательно отложено. Каждый пункт: что, почему не критично, как исправить.

- **Лимит частоты на картинки страниц руководства считается по IP из `X-Forwarded-For`**
  (`app/api.py`, `_client_key`). За Caddy на стенде заголовок ставит сам прокси. При запуске
  без прокси клиент может подменить заголовок и обойти лимит. Не критично: отдаются только
  страницы, на которые уже сослался код (`cited_pages`), поэтому руководство перебором не выкачать.
  Исправление: доверять `X-Forwarded-For`, только если запрос пришёл от прокси из списка
  в `.env`, иначе брать `request.client.host`.

- **Сбой SQLite после ответа ТОиР оставляет черновик в статусе «отправляется»**
  (`app/policy/tickets.py`, `confirm_draft`). Если после запроса в ТОиР упадёт запись в SQLite
  (`complete_ticket`, `release_ticket`, `mark_ticket_unknown` — например, `database is locked`),
  черновик и резерв проверки останутся в `sending`. Дубля заявки и ложного «отменён» нет: повтор
  и отмена заблокированы. Не критично: одна запись в локальную SQLite на одного механика, сбой
  маловероятен. Исправление: повторять запись статуса с паузой и при окончательной неудаче
  помечать `unknown` при следующем чтении черновика.

- **Нормальная проверка без `anomaly_score` по-разному трактуется в оценке тенденции и в
  остальных правилах** (`app/policy/trend.py`, `_failed`). Тенденция считает непригодной любую
  проверку без `anomaly_score`, а память по ТС (`history.py`) и «Главный механик»
  (`fleet_status.py`) — только отклонение без него. Тогда норма без числа рвала бы ряд
  тенденции, но в истории и статусе считалась бы нормой. Не критично: в данных заглушки у всех
  нормальных проверок `anomaly_score` есть. Исправление: одна функция «проверка пригодна» в
  `policy/` для всех трёх модулей; для нормы без числа — точка без значения на графике, но
  не сбой записи.

- **Невнятная ошибка у `get_trend` и `get_vehicle_history`, если выбранной проверки нет
  в `vehicles.json`** (`app/agent/tools.py`). Ряд проверок берётся из `vehicles.json`, а не из
  ответа ML. Если ML знает проверку, которой там нет, функции выбрасывают `KeyError`, агентный
  цикл его перехватывает, и модель получает «инструмент завершился ошибкой». Ход не падает,
  выводов о двигателе нет. Не критично: на демо список проверок и заглушка ML берут данные из
  одного файла. Исправление: вернуть модели понятную причину «истории по этой проверке нет».

- **Расширение запроса для вопроса «можно ли доехать» сформулировано как запрет**
  (`config/query_expansions.json`, группа «движение с неисправностью»). К вопросу дописываются
  слова «немедленно прекратить эксплуатацию… не заводить до устранения неисправности», поэтому
  выше поднимаются фрагменты с запретом. Если в руководстве для какой-то неисправности разрешено
  доехать с ограничениями, такой фрагмент может опуститься в выдаче. Сейчас на цифры не влияет:
  все ожидаемые страницы С2 в золотом наборе говорят о запрете. Исправление: добавить в золотой
  набор вопросы с разрешающим ответом и проверить нейтральную формулировку («эксплуатация при
  неисправности, допускается ли движение, ограничения»).

- **Нет автоматической оценки текста ответов агента** (идея). Золотой набор (`eval/`) проверяет
  только поиск: есть ли нужная страница в выдаче. Код гарантирует, что каждая ссылка взята из
  выдачи этого хода и относится к документам этого двигателя, но не проверяет, что ответ полный.
  Например, если руководство даёт два значения норматива, а агент назвал одно, ни валидатор, ни
  тесты этого не заметят: правило о расхождениях держится на промпте (`app/agent/prompts.py`).
  Сейчас это проверяется вручную, живыми прогонами. Идея: отдельный набор в `eval/` — вопрос,
  машина и ожидаемые ключевые признаки ответа (названы оба значения, есть ссылка на каждую
  ожидаемую страницу, нет цифр без ссылки, отказ для вопросов вне базы). Прогон через настоящего
  агента, проверка кодом по ссылкам и числам из выдачи, без длинных цитат руководств в репозитории.
