# Цифровой механик

AI-агент для механика автопарка. Берёт результат акустической проверки двигателя из ML-сервиса,
объясняет отклонение и риск строго по руководству на двигатель этой машины, отвечает на вопросы
со ссылкой «документ + страница PDF» и по подтверждению механика отправляет заявку на дефектовку в ТОиР.

Хакатон «ИИкузница», трек «Цифровой аватар».
Стенд: https://demo-mechanic.juliaplavinsky.ru (вход по паролю — передаётся жюри вместе с адресом).

## Схема

```
 Механик (браузер, телефон)
     │  чат, кнопка «Отправить в ТОиР», график, «Главный механик»
     ▼
 ┌──────────────────────── mechanic-web (FastAPI) ────────────────────────┐
 │  api.py ── SSE-чат ──► agent/loop.py  цикл tool calling (LLM)           │
 │                          │  набор инструментов задаёт policy/modes.py   │
 │                          ├─ get_diagnosis ──► integrations/ml_client ───┼──► ML-сервис  POST /diagnose
 │                          │                    policy/sanitize (описание ML — данные, не инструкции)
 │                          ├─ search_manual ──► retrieval/search          │
 │                          │     фильтр по двигателю ставит код;           │
 │                          │     BM25 + эмбеддинги, расширение запроса     │
 │                          ├─ get_vehicle_history / get_trend ──► policy/ (без LLM)
 │                          └─ draft_ticket ──► policy/ticket_validator    │
 │  ответ: ссылки подставляет policy/citations по chunk_id выдачи          │
 │  кнопка механика ──► policy/tickets (id + хэш черновика) ──────────────┼──► ТОиР  POST /tickets
 │  storage/: SQLite — заявки, журнал событий по машине, учёт вызовов LLM  │
 └─────────────────────────────────────────────────────────────────────────┘
     ▲ только чтение
 KB_DIR (PDF + kb.yaml)   INDEX_DIR (фрагменты, эмбеддинги)   ← вне репозитория и образа
```

Агент сам выбирает инструмент; сценарий не зашит цепочкой условий. Код ограничивает только
**набор** доступных инструментов по режиму проверки (при сбое записи или коде, невозможном для
двигателя, инструмента заявки у модели нет) и проверяет всё, что модель отдаёт наружу.

## Запуск за 5 минут

Нужны: Python 3.12+ или Docker, ключ OpenAI-совместимого провайдера, ссылка на материалы задачи.

```bash
cp .env.example .env                 # Windows: copy .env.example .env
# в .env: OPENAI_API_KEY, AGENT_MODEL, EMBEDDING_MODEL, VISION_MODEL, KB_DIR, INDEX_DIR, MATERIALS_URL;
#         APP_PASSWORD (или AUTH_DISABLED=1 только локально)
python scripts/fetch_materials.py    # PDF руководств → KB_DIR, vehicles.json → mocks/data/ (по MATERIALS_URL)
python scripts/ocr_scans.py          # один раз: распознавание сканов и испорченных страниц (VISION_MODEL)
python scripts/build_index.py        # KB_DIR → INDEX_DIR: фрагменты + эмбеддинги
```

`scripts/*.py` нужны зависимости из `requirements.txt` (кроме `fetch_materials.py` — он только на
стандартной библиотеке). Распознавание — около 140 вызовов vision-модели (≈ 430 ₽ на `gpt-6.2-astra`,
~15 мин); без `VISION_MODEL` шаг пропускается, и страницы-сканы останутся без текста. Индекс
демо-стенда собран после ручной сверки цифр распознанных страниц (см. «Распознавание»), поэтому
повторное распознавание может дать немного другой текст.

### Вариант 1. Docker (Windows, Linux, macOS)

```bash
docker compose -f docker-compose.yml -f docker-compose.local.yml up --build
```

Откройте http://127.0.0.1:8000. Поднимаются три контейнера: `mechanic-web` и две заглушки
организаторов (`mock-ml`, `mock-toir`) во внутренней сети. База знаний и индекс монтируются
из `KB_DIR` / `INDEX_DIR` только на чтение.

### Вариант 2. Без Docker

Windows (PowerShell):

```powershell
python -m venv .venv
.\.venv\Scripts\pip install -r requirements.txt -r mocks\requirements.txt
.\scripts\run_local.ps1
```

Linux / macOS:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt -r mocks/requirements.txt
sh scripts/run_local.sh
```

Скрипт запускает заглушки ML (порт 8001) и ТОиР (8002) и приложение на http://127.0.0.1:8000.

> Windows: если в системе задана переменная `OPENAI_API_KEY`, она перекрывает значение из `.env`.

## Как заменить заглушки рабочими сервисами

Контракт — ТЗ v6, раздел 5; схемы — `mocks/openapi_ml.json`, `mocks/openapi_toir.json`.

1. **Сервис с тем же контрактом** — достаточно поменять `MOCK_ML_URL` и `MOCK_TOIR_URL` в `.env`
   (`POST {MOCK_ML_URL}/diagnose`, `POST {MOCK_TOIR_URL}/tickets`). Код не меняется.
2. **Другой контракт** — написать адаптер, реализующий протокол `DiagnosticsService`
   (`app/integrations/ml_client.py`) или `TicketService` (`app/integrations/toir_client.py`),
   и подставить его в `create_app` (`app/main.py`). Агент, политики и валидатор работают
   с моделями `Diagnosis` / `TicketRequest` и от транспорта не зависят.
3. **Список машин и история проверок** берутся из `vehicles.json` (заглушка ML списка не отдаёт);
   для рабочей системы — заменить загрузчик в `app/integrations/fleet.py` на источник парка.

## Как добавить руководство или двигатель

1. Положить PDF в материалы (или в `KB_DIR`).
2. Добавить запись в `config/kb.yaml`: `doc_id`, обозначение `manual` (ровно как пойдёт в заявку),
   `file`, `engine_family`, `kind`, `pages`, `sha256`; правила извлечения — `page_number_offset`,
   `strip_patterns` (колонтитулы), `title_band`. Поля описаны в `kb.example.yaml`.
3. Новый двигатель — семейство в `config/engines.json` (какие `engine_model` из карточки ТС к нему
   относятся) и коды, невозможные для него, в `config/fault_applicability.json` со страницами-доказательствами.
4. Страницы-сканы и страницы с испорченным текстовым слоем — в `scan_pages`;
   `python scripts/ocr_scans.py`, затем `python scripts/check_ocr_digits.py` и ручная сверка расхождений.
5. `python scripts/build_index.py`, вопросы по новому руководству — в `eval/golden.jsonl`,
   `python -m eval.run_eval`.

Код при этом не меняется: фильтр поиска по двигателю строится из манифеста и `engines.json`.

## Материалы задачи: руководства и данные заглушек

PDF руководств и данные заглушек (карточки машин, ответы диагностической системы) в репозиторий
не коммитятся — это документы правообладателей (п. 9.1); в `.gitignore` — `*.pdf`, `*.zip`, `*.docx`,
`mocks/data/vehicles.json`, `.env`. При развёртывании их загружает `scripts/fetch_materials.py`
по ссылке из переменной `MATERIALS_URL` (публичная папка Яндекс Диска из материалов задачи):

- PDF кладутся в `KB_DIR` под именами из манифеста `config/kb.yaml` — сопоставление по sha256,
  файл с неизвестным хэшем пропускается, уже скачанный не перекачивается;
- из архива заглушек берётся `data/vehicles.json` → `mocks/data/` (сверяется и `fault_types.json`);
- манифест `config/kb.yaml` копируется в `KB_DIR/kb.yaml`; права — каталог 700, файлы 600.

`fault_types.json` (справочник кодов F01–F14) — в репозитории. Ключи и пароли — только в `.env`;
на ключе LLM стенда установлен лимит расходов. Индекс (производное от руководств) тоже вне
репозитория и образа; на стенде — в каталоге с правами 700.

## Как устроено

```
app/
  main.py            FastAPI, отдача интерфейса, доступ по паролю (auth.py)
  api.py             тонкий HTTP-слой: SSE-чат с агентом, подтверждение заявки, страницы PDF,
                     «Главный механик», тенденция
  agent/             цикл агента на tool calling, инструменты, промпты
  policy/            правила без LLM: режим проверки, применимость кода, приоритет, валидатор
                     заявки, ссылки, история машины, тенденция, статус парка
  retrieval/         извлечение PDF, нарезка, распознавание (сверка цифр), гибридный поиск
  integrations/      клиенты ML и ТОиР за интерфейсами, данные парка
  storage/           SQLite: заявки, журнал событий, учёт вызовов LLM
  web/               одна страница HTML + JS без сборки
config/              манифест базы знаний, семейства двигателей, применимость кодов F01…F14,
                     пороги политик, словарь расширения запроса, цены для расчёта стоимости
scripts/             загрузка материалов, распознавание, индексация, сверка цифр, стоимость
eval/                золотой набор вопросов для поиска и скрипт оценки
mocks/               заглушки организаторов (код не изменялся; данные — по ссылке)
```

### Инструменты агента

| Инструмент | Что делает | Доступен (`app/policy/modes.py`) |
|---|---|---|
| `get_diagnosis` | результат выбранной проверки (статус, код, выраженность, уверенность, качество) | пока результат не получен |
| `search_manual` | поиск по руководствам двигателя этой машины; фильтр по двигателю ставит код | всегда |
| `get_vehicle_history` | B1: прошлые проверки и наши заявки, повторы кода, норма после отклонения | норма, отклонение |
| `get_trend` | B2: тенденция `anomaly_score` по 3–5 проверкам, дни до порога карантина (детерминированно) | норма, отклонение |
| `draft_ticket` | черновик заявки; проверяет валидатор, отправляет механик кнопкой | только отклонение (не при сбое записи и не при коде, невозможном для двигателя) |

Повторную заявку по той же проверке не пропускает `app/policy/tickets.py`: одна проверка — одна заявка.

B3 «Главный механик» (норма / требует внимания / карантин, приоритетный список, история) считается
кодом в `policy/fleet_status.py`, без модели.

### Где обеспечиваются правила продукта (кодом, а не промптом)

| Правило | Где |
|---|---|
| Ссылки только на фрагменты из выдачи этого хода; документ и страницу подставляет код | `app/policy/citations.py` |
| Номер страницы = индекс PDF; колонтитулы и напечатанные номера вырезаются | `app/retrieval/extract.py`, `app/retrieval/build.py` |
| Поиск фильтруется по документам двигателя выбранной машины | `app/retrieval/search.py`, `app/agent/tools.py` |
| check_failed / плохое качество → нет выводов и нет инструмента заявки | `app/policy/modes.py` |
| Помехи, низкая уверенность, посторонний текст — первой строкой ответа | `app/policy/modes.py`, `app/agent/loop.py` |
| Посторонний текст в `description` ML вырезается до модели | `app/policy/sanitize.py` |
| Код неисправности не подходит двигателю → заявка не создаётся | `app/policy/applicability.py`, `config/fault_applicability.json` |
| Валидатор заявки: статус, качество, машина, тип, работы, ссылки, номера деталей буквально из фрагмента | `app/policy/ticket_validator.py` |
| Заявку отправляет механик кнопкой; подтверждение по id и хэшу черновика; одна проверка — одна заявка | `app/policy/tickets.py` |
| Приоритет — детерминированная функция с причинами | `app/policy/urgency.py`, `config/policy.json` |

Журнал событий по каждой машине — таблица `events` в SQLite и JSON-строки в stdout;
каждый вызов LLM и эмбеддингов — таблица `llm_calls` (для расчёта стоимости).

### Поиск по руководствам

- **Извлечение** (PyMuPDF): текст с вёрсткой; таблицы, набранные поперёк листа (карты дефектации
  236.01.01 РК), читаются в координатах альбомного листа; таблица — один фрагмент, фрагмент не
  пересекает страницу.
- **Нарезка**: по заголовкам; раздел (`section`) — только настоящий заголовок, пункт-предложение
  раздел не задаёт; ближайший пункт идёт в эмбеддинг.
- **Поиск**: BM25 + эмбеддинги, слияние RRF; индекс каждого семейства двигателей отдельно —
  фрагмент чужого двигателя в выдачу попасть не может. Разговорные формулировки механика
  («своим ходом перегнать») дополняются терминами руководств по словарю `config/query_expansions.json`.
- **Распознавание**: сканы и 57 страниц 236.01.01 РК с разрушенным текстовым слоем распознаны
  vision-моделью. Каждое число распознанного текста сверяется с цифрами текстового слоя той же
  страницы (`scripts/check_ocr_digits.py`), расхождения сверены вручную; сканы без слоя прочитаны
  дважды и сравнены.
- **Качество** (`eval/golden.jsonl`, 29 вопросов по 4 двигателям + 4 вне базы): нужная страница
  в первых пяти — 29/29, первой — 17/29; фрагментов другого двигателя в выдаче — 0.
  История прогонов — `eval/history.csv`.

## Стоимость

`python scripts/cost_report.py` считает по журналу `llm_calls` (цены и курс — `config/cost.json`):

- одна сессия проверки (объяснение + 2 вопроса + заявка) — **≈ 2,61 ₽** на `gpt-6.2-sol`
  (`docs/cost.csv`, формат калькулятора организаторов);
- парк 50 машин, проверка раз в 17 дней — **≈ 138 ₽ в месяц** (`docs/cost_fleet.csv`);
- разово: индексация и распознавание — ≈ 450 ₽.

## Ограничения

Полный список с причинами и способами исправления — `docs/UNIMPLEMENTED.md`. Главное:

- Номера деталей из распознанных страниц валидатор принимает как написанные в руководстве;
  от ошибок распознавания защищают сверка с текстовым слоем, ручная сверка расхождений и двойное
  прочтение сканов, но не полностью.
- Правило «называть все значения норматива при расхождении в руководстве» — в промпте, кодом
  не проверяется; автоматической оценки текста ответов нет (только поиска).
- Редкие написания номеров деталей дают отказ валидатора на честной заявке (сторона безопасная).
- Расширение запроса для «можно ли доехать» поднимает фрагменты с запретом эксплуатации.
- Пожелания заказчика с брифинга (голос, мультиязычность, поиск запчастей в интернете,
  фото госномера) не реализованы.
